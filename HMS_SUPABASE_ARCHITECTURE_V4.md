## 1. Executive Summary & V4 Hardening Objectives

The V3 architecture established the core relational foundation: a single unified `students` model, removal of `beds.is_occupied`, relational `room_allocations`, and multi-hostel warden assignments. 

However, a rigorous security and concurrency audit identified 11 critical blockers in V3 that would permit privilege escalation, data loss, state drift, and concurrency deadlocks if implemented as previously drafted.

### Key V4 Hardening Fixes:
1. **Un-Bypassable Structural Room/Bed Integrity**: Direct client `INSERT/UPDATE/DELETE` on `hostel_rooms` and `beds` is completely **REVOKED**. Admins must use controlled RPCs (`create_room_with_beds`, `resize_room_capacity`, `decommission_room`), mathematically guaranteeing that $\text{COUNT}(\text{beds}) \equiv \text{capacity}$.
2. **Column-Level Privilege Controls & Anti-Escalation**:
   - `profiles`: Direct `UPDATE` is revoked on sensitive columns (`role`, `is_active`, `legacy_django_id`, `email`). Self-service updates are restricted to `phone` and `avatar_url` via strict RLS column checks or dedicated RPC.
   - `students`: Institutional fields (`enrollment_no`, `course_id`, `no_dues`) cannot be updated by students or wardens outside their assigned scope.
3. **Controlled Gate Pass Transitions**: Direct client `UPDATE` on `gate_passes` is revoked. State changes occur exclusively via `approve_gate_pass`, `reject_gate_pass`, and `log_gate_movement` RPCs.
4. **Permanent Historical Record Retention**: Destructive `ON DELETE CASCADE` is eliminated on historical relationships (`issues`, `gate_passes`, `visitor_logs`, `room_allocations`). Soft-delete lifecycles (`students.status`, `hostel_rooms.is_active`) prevent data loss when residents depart or rooms are decommissioned.
5. **Deterministic Universal Lock Order**: Defined an unalterable global lock order across all transactional procedures: **Hostels $\rightarrow$ Rooms $\rightarrow$ Beds (Ascending ID) $\rightarrow$ Students (Ascending ID) $\rightarrow$ Allocations**.
6. **Visitor Log Historical Location Snapshot**: Corrected schema contradiction by adding `room_id` to `visitor_logs` and populating both `hostel_id` and `room_id` via a trigger snapshotting the resident's active allocation at creation time.
7. **Safe Meal-Skip Uniqueness**: Made `student_meal_skips.meal_type_id NOT NULL` to eliminate PostgreSQL's multiple-NULL loophole in unique constraints.
8. **Hardened `SECURITY DEFINER` Privileges**: Every RPC has explicit `REVOKE EXECUTE ... FROM PUBLIC`, explicit grants to `authenticated`, and fixed search paths (`SET search_path = public, pg_temp`).

## 3. Structural Room & Bed Integrity (RPC-Enforced)

To prevent administrators or buggy scripts from violating the $\text{COUNT}(\text{beds}) \equiv \text{capacity}$ invariant:
1. **Direct client permissions**: `REVOKE INSERT, UPDATE, DELETE ON public.hostel_rooms, public.beds FROM PUBLIC, authenticated;`
2. **Controlled RPC Interface**: Room creation, resizing, and decommissioning are performed strictly through these atomic functions:

### 3.1 `create_room_with_beds`
```sql
CREATE OR REPLACE FUNCTION public.create_room_with_beds(
  p_hostel_id BIGINT,
  p_room_no TEXT,
  p_floor INTEGER,
  p_capacity INTEGER,
  p_room_type CHAR(1) DEFAULT 'D'
)
RETURNS BIGINT
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public, pg_temp
AS $$
DECLARE
  v_new_room_id BIGINT;
  i INTEGER;
BEGIN
  IF auth.user_role() != 'ADMIN' THEN
    RAISE EXCEPTION 'Access Denied: Only Admins can create rooms';
  END IF;
  IF p_capacity < 1 THEN
    RAISE EXCEPTION 'Capacity must be at least 1';
  END IF;

  INSERT INTO public.hostel_rooms (hostel_id, no, floor, capacity, room_type)
  VALUES (p_hostel_id, p_room_no, p_floor, p_capacity, p_room_type)
  RETURNING id INTO v_new_room_id;

  FOR i IN 1..p_capacity LOOP
    INSERT INTO public.beds (room_id, bed_number)
    VALUES (v_new_room_id, i::TEXT);
  END LOOP;

  RETURN v_new_room_id;
END;
$$;
```

### 3.2 `resize_room_capacity`
```sql
CREATE OR REPLACE FUNCTION public.resize_room_capacity(
  p_room_id BIGINT,
  p_new_capacity INTEGER
)
RETURNS JSONB
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public, pg_temp
AS $$
DECLARE
  v_old_capacity INTEGER;
  v_occupied_beds_in_excess INTEGER;
  i INTEGER;
BEGIN
  IF auth.user_role() != 'ADMIN' THEN
    RAISE EXCEPTION 'Access Denied: Only Admins can resize room capacity';
  END IF;
  IF p_new_capacity < 1 THEN
    RAISE EXCEPTION 'Capacity must be at least 1';
  END IF;

  SELECT capacity INTO v_old_capacity 
  FROM public.hostel_rooms 
  WHERE id = p_room_id FOR UPDATE;

  IF NOT FOUND THEN RAISE EXCEPTION 'Room % not found', p_room_id; END IF;
  IF p_new_capacity = v_old_capacity THEN
    RETURN jsonb_build_object('success', true, 'message', 'Capacity unchanged');
  END IF;

  IF p_new_capacity > v_old_capacity THEN
    -- Expanding capacity: Add beds
    UPDATE public.hostel_rooms SET capacity = p_new_capacity, updated_at = NOW() WHERE id = p_room_id;
    FOR i IN (v_old_capacity + 1)..p_new_capacity LOOP
      INSERT INTO public.beds (room_id, bed_number) VALUES (p_room_id, i::TEXT);
    END LOOP;
  ELSE
    -- Shrinking capacity: Check if beds beyond new capacity are occupied
    SELECT COUNT(*) INTO v_occupied_beds_in_excess
    FROM public.beds b
    JOIN public.room_allocations a ON a.bed_id = b.id AND a.is_active = TRUE
    WHERE b.room_id = p_room_id AND b.bed_number::INTEGER > p_new_capacity;

    IF v_occupied_beds_in_excess > 0 THEN
      RAISE EXCEPTION 'Cannot reduce capacity: % bed(s) in the reduction zone are currently occupied. Vacate or reassign residents first.', v_occupied_beds_in_excess;
    END IF;

    -- Delete vacant beds in the reduction range
    DELETE FROM public.beds
    WHERE room_id = p_room_id AND bed_number::INTEGER > p_new_capacity;

    UPDATE public.hostel_rooms SET capacity = p_new_capacity, updated_at = NOW() WHERE id = p_room_id;
  END IF;

  RETURN jsonb_build_object('success', true, 'room_id', p_room_id, 'old_capacity', v_old_capacity, 'new_capacity', p_new_capacity);
END;
$$;
```

### 3.3 `decommission_room` (Safe Deletion Alternative)
Rooms with historical records (`issues`, `gate_passes`, `visitor_logs`, `room_allocations`) **cannot be physically deleted** due to `ON DELETE RESTRICT`. Instead, admins decommission rooms safely:
```sql
CREATE OR REPLACE FUNCTION public.decommission_room(p_room_id BIGINT)
RETURNS JSONB
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public, pg_temp
AS $$
BEGIN
  IF auth.user_role() != 'ADMIN' THEN
    RAISE EXCEPTION 'Access Denied: Only Admins can decommission rooms';
  END IF;

  -- Verify no active allocations exist
  IF EXISTS (
    SELECT 1 FROM public.beds b
    JOIN public.room_allocations a ON a.bed_id = b.id AND a.is_active = TRUE
    WHERE b.room_id = p_room_id
  ) THEN
    RAISE EXCEPTION 'Cannot decommission room: Residents are currently allocated. Vacate all beds first.';
  END IF;

  UPDATE public.hostel_rooms SET is_active = FALSE, updated_at = NOW() WHERE id = p_room_id;
  RETURN jsonb_build_object('success', true, 'room_id', p_room_id, 'is_active', false);
END;
$$;
```

## 4. Column-Level Permission & Security Hardening

### 4.1 Column Mutation Matrix
To prevent privilege escalation and unauthorized modification of institutional records:

| Table | Column(s) | ADMIN | WARDEN | SECURITY | STUDENT |
| :--- | :--- | :---: | :---: | :---: | :---: |
| **`profiles`** | `role`, `is_active`, `legacy_django_id`, `email` | **YES** | NO | NO | NO |
| **`profiles`** | `first_name`, `last_name` | **YES** | NO | NO | NO |

### 4.2 Database Enforcement via Dedicated Profile Update RPC
Rather than relying on client conventions, user self-service updates are routed through a dedicated function:
```sql
CREATE OR REPLACE FUNCTION public.update_my_profile(
  p_phone TEXT,
  p_avatar_url TEXT
)
RETURNS JSONB
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public, pg_temp
AS $$
BEGIN
  UPDATE public.profiles
  SET phone = p_phone,
      avatar_url = p_avatar_url,
      updated_at = NOW()
  WHERE id = auth.uid();

  -- Synchronize contact number to students table if caller is a resident
  UPDATE public.students
  SET phone = p_phone, updated_at = NOW()
  WHERE profile_id = auth.uid();

  RETURN jsonb_build_object('success', true, 'profile_id', auth.uid());
END;
$$;
```
Direct `UPDATE` on `profiles` is granted **only to ADMIN**.

## 5. Controlled Gate Pass Workflow & Expiration

### 5.1 Gate Pass State Machine & Transitions
Direct client `UPDATE` on `public.gate_passes` is **REVOKED from all roles**. All state transitions occur through controlled functions:

```text
               ┌──────────────┐
               │   PENDING    │
               └──────┬───────┘
                      │
          ┌───────────┴───────────┐
          │ (approve_gate_pass)   │ (reject_gate_pass)
          ▼                       ▼
   ┌──────────────┐        ┌──────────────┐
   │   APPROVED   │        │   REJECTED   │ (Terminal)
   └──────┬───────┘        └──────────────┘
          │
          │ (log_gate_movement: 'EXIT')
          ▼
   ┌──────────────┐
   │   OUTSIDE    │ (actual_exit_time IS NOT NULL, actual_entry_time IS NULL)
   └──────┬───────┘
          │
          │ (log_gate_movement: 'ENTRY')
          ▼
   ┌──────────────┐
   │  COMPLETED   │ (Terminal, is_late computed automatically)
   └──────────────┘
```

### 5.2 Expiration Rules vs. Late Return Principle
1. **Unused Approved Passes**: An approved pass where `NOW() > (expected_return_date + expected_return_time)` and `actual_exit_time IS NULL` is considered **EXPIRED**. The student never left campus. The `log_gate_movement` RPC will **strictly reject** an `EXIT` attempt on an expired pass.
2. **Late Return**: If a student successfully exited on time, but returns after the expected return timestamp, `ENTRY` is **PERMITTED** to allow the student back into the hostel safely, but `is_late` is automatically stamped `TRUE` by the database engine.
3. **Completed Passes**: Once `status = 'completed'`, the UUID token is permanently burned and cannot be scanned for movement again.

### 5.3 Gate Pass Approval RPCs
```sql
CREATE OR REPLACE FUNCTION public.approve_gate_pass(
  p_pass_id BIGINT,
  p_note TEXT DEFAULT ''
)
RETURNS JSONB
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public, pg_temp
AS $$
DECLARE
  v_caller_role TEXT;
  v_hostel_id BIGINT;
  v_status TEXT;
BEGIN
  v_caller_role := auth.user_role();
  IF v_caller_role NOT IN ('ADMIN', 'WARDEN') THEN
    RAISE EXCEPTION 'Access Denied: Only Admins and Wardens can approve gate passes';
  END IF;

  SELECT hostel_id, status INTO v_hostel_id, v_status
  FROM public.gate_passes WHERE id = p_pass_id FOR UPDATE;

  IF NOT FOUND THEN RAISE EXCEPTION 'Gate pass % not found', p_pass_id; END IF;
  IF v_status != 'pending' THEN RAISE EXCEPTION 'Only pending passes can be approved (Current: %)', v_status; END IF;

  IF v_caller_role = 'WARDEN' AND NOT EXISTS (
    SELECT 1 FROM public.warden_hostel_assignments 
    WHERE warden_profile_id = auth.uid() AND hostel_id = v_hostel_id
  ) THEN
    RAISE EXCEPTION 'Access Denied: You cannot approve passes for an unassigned hostel block';
  END IF;

  UPDATE public.gate_passes
  SET status = 'approved',
      approved_by = auth.uid(),
      action_note = p_note,
      actioned_at = NOW(),
      updated_at = NOW()
  WHERE id = p_pass_id;

  RETURN jsonb_build_object('success', true, 'pass_id', p_pass_id, 'status', 'approved');
END;
$$;
```

## 6. Historical Data Retention & Deletion Policy

### 6.1 Foreign Key Constraint Hardening
To prevent accidental erasure of institutional records:
- **`ON DELETE CASCADE`** is permitted **ONLY** on parent-child operational metadata:
  - `profiles` $\rightarrow$ `auth.users`
  - `menu_item_links` $\rightarrow$ `menus`, `menu_items`
  - `warden_hostel_assignments` $\rightarrow$ `profiles`
- **`ON DELETE RESTRICT`** is enforced on all historical relations:
  - `room_allocations.student_id` $\rightarrow$ `ON DELETE RESTRICT`
  - `room_allocations.bed_id` $\rightarrow$ `ON DELETE RESTRICT`
  - `issues.student_id`, `issues.hostel_id`, `issues.room_id` $\rightarrow$ `ON DELETE RESTRICT`
  - `gate_passes.student_id`, `gate_passes.hostel_id`, `gate_passes.room_id` $\rightarrow$ `ON DELETE RESTRICT`
  - `visitor_logs.student_id`, `visitor_logs.hostel_id`, `visitor_logs.room_id` $\rightarrow$ `ON DELETE RESTRICT`
  - `student_meal_skips.student_id`, `student_meal_skips.hostel_id` $\rightarrow$ `ON DELETE RESTRICT`

### 6.2 Student Lifecycle Management (Soft-Delete)
When a student graduates or withdraws from the institution, their record is **never physically deleted from `students`**:
- Instead, `students.status` is set to `'ALUMNI'` or `'WITHDRAWN'`.
- Their active room allocation is vacated via `vacate_student_room`.
- Historical complaints, gate movements, and visitor records remain intact and queryable for audits.

## 7. Universal Deterministic Lock Order

To mathematically eliminate transaction deadlocks during concurrent multi-row operations, every RPC in the system strictly adheres to the following universal lock hierarchy:

```text
Universal Lock Hierarchy (Acquired via SELECT ... FOR UPDATE):
  Level 1: public.hostels                 (Lock in shared or exclusive mode)
  Level 2: public.hostel_rooms            (Lock in exclusive mode)
  Level 3: public.beds                    (Order by id ASC if locking multiple beds)
  Level 4: public.students                (Order by id ASC if locking multiple students)
  Level 5: public.room_allocations        (Lock target active allocations)
  Level 6: Operational records            (issues, gate_passes, visitor_logs)
```

### Reallocation Lock Order Trace (`allocate_student_room`)
When reallocating a student from Room 101 (Bed 1) to Room 202 (Bed 5):
1. Lock Room 101 and Room 202 in deterministic order: `WHERE id IN (room_old, room_new) ORDER BY id ASC FOR UPDATE`.
2. Lock Bed 1 and Bed 5 in deterministic order: `WHERE id IN (bed_old, bed_new) ORDER BY id ASC FOR UPDATE`.
3. Lock Student: `WHERE id = p_student_id FOR UPDATE`.
4. Lock Active Allocation: `WHERE student_id = p_student_id AND is_active = TRUE FOR UPDATE`.
5. Perform deactivation and new insertion $\rightarrow$ Commit.

## 8. Historical Snapshot Trigger Specification

To guarantee that maintenance tickets, gate passes, and visitor records capture the resident's physical location at creation time without trusting client input:

| Entity | `student_id` | `hostel_id` Snapshot | `room_id` Snapshot | Reason |
| :--- | :---: | :---: | :---: | :--- |
| **`issues`** | YES | YES | YES | Maintenance ticket belongs permanently to the room where fault occurred. |
| **`gate_passes`** | YES | YES | YES | Movement history captures the student's residential room at time of exit. |
| **`visitor_logs`** | YES | YES | YES | Visitor register records the room visited during that historical check-in. |
| **`student_meal_skips`**| YES | YES | NO | Dining is managed at the hostel block level; room number is irrelevant. |

### Immutable Snapshot Trigger Implementation
```sql
CREATE OR REPLACE FUNCTION public.trig_fn_snapshot_student_location()
RETURNS TRIGGER AS $$
DECLARE
  v_hostel_id BIGINT;
  v_room_id BIGINT;
BEGIN
  -- Resolve active room allocation for the student
  SELECT r.hostel_id, r.id INTO v_hostel_id, v_room_id
  FROM public.room_allocations a
  JOIN public.beds b ON a.bed_id = b.id
  JOIN public.hostel_rooms r ON b.room_id = r.id
  WHERE a.student_id = NEW.student_id AND a.is_active = TRUE;

  IF NOT FOUND THEN
    RAISE EXCEPTION 'Cannot create record: Student % has no active room allocation.', NEW.student_id;
  END IF;

  NEW.hostel_id := v_hostel_id;
  IF TG_TABLE_NAME IN ('issues', 'gate_passes', 'visitor_logs') THEN
    NEW.room_id := v_room_id;
  END IF;

  RETURN NEW;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER SET search_path = public, pg_temp;

-- Attach to historical tables
CREATE TRIGGER tr_snapshot_issues_loc BEFORE INSERT ON public.issues
FOR EACH ROW EXECUTE FUNCTION public.trig_fn_snapshot_student_location();

CREATE TRIGGER tr_snapshot_gate_loc BEFORE INSERT ON public.gate_passes
FOR EACH ROW EXECUTE FUNCTION public.trig_fn_snapshot_student_location();

CREATE TRIGGER tr_snapshot_visitor_loc BEFORE INSERT ON public.visitor_logs
FOR EACH ROW EXECUTE FUNCTION public.trig_fn_snapshot_student_location();

CREATE TRIGGER tr_snapshot_mealskip_loc BEFORE INSERT ON public.student_meal_skips
FOR EACH ROW EXECUTE FUNCTION public.trig_fn_snapshot_student_location();
```

## 11. Dashboard & Analytical Security Scoping

To prevent wardens or security guards from accessing unauthorized global operational data:
1. **`view_admin_dashboard_stats`**: Granted strictly to `ADMIN`.
2. **`view_warden_dashboard_stats`**: Security Invoker View filtered by `auth.get_warden_hostel_ids(auth.uid())`. A warden sees metrics **only for their assigned blocks**.

```sql
-- Warden Operational Scoped View
CREATE OR REPLACE VIEW public.view_warden_dashboard_stats 
WITH (security_invoker = true) AS
SELECT 
  h.id AS hostel_id,
  h.name AS hostel_name,
  h.gender,
  h.floor_count,
  COUNT(DISTINCT hr.id) AS total_rooms,
  COUNT(DISTINCT b.id) AS total_capacity,
  COUNT(DISTINCT a.id) FILTER (WHERE a.is_active = TRUE) AS occupied_beds,
  COUNT(DISTINCT b.id) - COUNT(DISTINCT a.id) FILTER (WHERE a.is_active = TRUE) AS vacant_beds,
  (SELECT COUNT(*) FROM public.gate_passes gp WHERE gp.hostel_id = h.id AND gp.status = 'pending') AS pending_gate_passes,
  (SELECT COUNT(*) FROM public.issues iss WHERE iss.hostel_id = h.id AND iss.status != 'completed') AS open_issues
FROM public.hostels h
JOIN public.warden_hostel_assignments wha ON wha.hostel_id = h.id AND wha.warden_profile_id = auth.uid()
LEFT JOIN public.hostel_rooms hr ON hr.hostel_id = h.id AND hr.is_active = TRUE
LEFT JOIN public.beds b ON b.room_id = hr.id
LEFT JOIN public.room_allocations a ON a.bed_id = b.id AND a.is_active = TRUE
GROUP BY h.id, h.name, h.gender, h.floor_count;
```

## 14. Final Architectural Invariants (The 33 Rules)

1. Every hostel resident exists in exactly one `students` table.
2. There is zero outside-student table, flag, serializer, route, or UI screen.
3. `students` contains zero room allocation state.
4. `beds` contains zero duplicated occupancy state (`beds.is_occupied` is deleted).
5. Room capacity is structurally defined by physical `beds` records ($\text{COUNT}(\text{beds}) \equiv \text{capacity}$).
6. Direct client mutations on `hostel_rooms` and `beds` are completely revoked.
7. A student has at most one active room allocation (`is_active = TRUE`).
8. A bed has at most one active room allocation (`is_active = TRUE`).
9. Allocation and reallocation operations are fully atomic.
10. Lock acquisition order across all transactions follows the universal hierarchy.
11. Wardens can access only students with active allocations in their assigned hostels.
12. Unallocated students are visible strictly to Admins.
13. `public.profiles.role` is the single source of authorization truth.
14. Direct client updates to `profiles.role` or `profiles.is_active` are prohibited.
15. Students can update only personal contact info via `update_my_profile`.
16. Gate-pass approval and rejection are controlled via RPCs.
17. Gate movement logging is atomic and strictly sequenced (`EXIT` before `ENTRY`).
18. Completed gate passes cannot be reused.
19. Approved passes that were never used for exit cannot be used after the expected return timestamp.
20. Entry after expected return time is permitted but flagged `is_late = TRUE`.
21. Historical records cannot be erased by deleting operational entities (`ON DELETE RESTRICT`).
22. Decommissioned rooms and departed students are preserved via soft-delete flags.
23. Issues, gate passes, and visitor logs snapshot `hostel_id` and `room_id` immutably at creation.
24. Issue status changes cannot bypass the `issue_updates` audit trail.
25. Direct client `UPDATE` on `issues.status` is revoked (managed via RPC).
26. `meal_type_id` on `student_meal_skips` is `NOT NULL`, guaranteeing unique skip per meal/date.
27. All `SECURITY DEFINER` functions have `REVOKE EXECUTE ... FROM PUBLIC`.
28. All `SECURITY DEFINER` functions enforce `SET search_path = public, pg_temp`.
29. Row Level Security is enabled and enforced across all public domain tables.
30. Direct table mutations are revoked for all RPC-managed business operations.
31. Dashboard analytics views enforce hostel scoping via security invoker policies.
32. The legacy `MessBilling` model is permanently excluded from migration.
33. Data migration preserves all historical foreign key relationships and identity mappings.
